# 评分标准 (Scoring Rubric)

## 总则

1. **每项 >= 90 分才能通过**
2. **存在任何红线则直接打回**
3. **评分应基于实际证据，不是猜测**

## 分数档位

| 档位 | 分数范围 | 含义 |
|------|----------|------|
| A | 90-100 | 优秀，无需改进即可发布 |
| B | 80-89 | 良好，有小问题建议改进 |
| C | 70-79 | 及格，有较多问题需修复 |
| D | 60-69 | 不及格，有严重问题 |
| F | <60 | 不可接受，需要重构 |

## 评分校准标准

### 高分标准 (90-100) ✅ PASS

必须满足**所有**条件：

- **功能完整**: 所有声明的功能都能正常工作
- **无已知 bug**: 没有明显影响使用的错误
- **边界处理**: 正确处理空值、异常、超时等边界情况
- **有证据**: 评分基于实际测试/运行结果，不是猜测
- **文档齐全**: 关键接口和使用方式有说明

扣分项（每项扣 2-5 分）：
- 有小的 UI 不一致或文字错误（-2 分/项）
- 有小的性能问题但不明显（-3 分）
- 有轻微的代码风格问题（-2 分）

### 中等分数 (70-89) ⚠️ FAIL

出现以下任一情况：

- **功能基本正常但有瑕疵**: 核心功能可用，但有影响体验的问题
- **边界处理不完整**: 某些异常情况处理不完善，但不会导致崩溃
- **缺少部分测试**: 有测试但覆盖不完整
- **文档不完整**: 有基本文档但缺少关键部分

典型扣分模式：
- 缺少测试: -10 分
- 有可重现的 bug: -15 分
- 错误处理不完善: -10 分
- 文档缺失: -8 分

### 低分标准 (60-69) ❌ FAIL

出现以下任一情况：

- **功能不完整**: 核心功能缺失或不可用
- **有影响使用的 bug**: 用户会经常遇到问题
- **架构有明显缺陷**: 代码难以维护或扩展
- **安全风险**: 有可利用的漏洞

### 严重不合格 (<60) 🚫 FAIL

出现以下任一情况：

- **功能完全不可用**: 应用无法启动或核心功能完全损坏
- **严重安全漏洞**: 可被直接利用的安全问题
- **数据丢失风险**: 可能导致用户数据损坏或丢失
- **完全无法维护**: 代码无法理解或修改

## 评分一致性规则

为保证评分一致性：

1. **每项扣分必须有具体证据**
   - 引用具体文件路径和行号
   - 引用测试失败输出
   - 引用运行时错误日志

2. **扣分时必须说明原因**
   - 不能只说 "代码质量差"
   - 要说 "在 bridge-api.ts:123 行，使用了 eval() 导致安全风险"

3. **分数变化应有理由说明**
   - Round 1 给 70 分
   - Round 2 变成 85 分
   - 必须说明修复了什么

4. **同一问题不重复扣分**
   - 如果一个问题影响多个维度，只扣一次分
   - 选择影响最大的维度扣分

## 常见评分误区

### ❌ 错误：分数通胀
```
"这个项目挺好的，应该给 88 分"
```
**正确做法**: 88 分意味着什么？必须列出具体问题。

### ❌ 错误：基于感受评分
```
"我觉得这个 UI 看起来不错"
```
**正确做法**: 引用具体的 UX 问题，如 "按钮太小(16x16px)，难以点击"。

### ❌ 错误：分数漂移
```
Round 1: 65 分
Round 2: 75 分（没修复什么）
```
**正确做法**: 分数变化必须有实际证据支撑。

### ✅ 正确：证据驱动评分
```
功能完整性: 85/100
- 扣分原因: /api/goal 端点缺少 POST 方法支持
- 证据: 尝试 POST 返回 404
- 影响: 用户无法创建新目标
```
