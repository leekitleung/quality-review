# 证据收集指南 (Evidence Collection Guide)

证据是评分的基础。没有证据的评分是不可接受的。

## 五项核心原则与证据要求

### P1: Goal 模式约束
**只描述最终状态，不写实现步骤**

证据要求：
- ✅ **目标达成证据**: 功能输出、API 响应、数据格式
- ✅ **验收条件满足**: 读取 `goal.md` 或 `SPEC.md`，验证每条是否满足
- ❌ **禁止**: 引用实现细节作为"目标达成"的证据

### P2: 执行门禁
**必须有真实测试/构建/文件证据**

证据层级（按优先级）：

| 层级 | 证据类型 | 可信度 |
|------|----------|--------|
| L1 | 自动化测试通过 | ⭐⭐⭐⭐⭐ |
| L2 | 构建成功 | ⭐⭐⭐⭐ |
| L3 | 类型检查通过 | ⭐⭐⭐ |
| L4 | 静态分析通过 | ⭐⭐ |
| L5 | 代码审查（主观） | ⭐ |

**评分规则**：
- L1 证据存在 + 满足目标 → 满分
- 只有 L5 证据 → 最多给 80 分
- 无任何证据 → 不及格

### P3: 对抗性审查
**独立 reviewer，不让执行模型自证完成**

证据来源规则：
- ✅ **允许**: 引用项目历史文件（不是你刚写的）
- ✅ **允许**: 引用已有测试的输出
- ✅ **允许**: 引用其他 Reviewer 的报告
- ❌ **禁止**: 引用你自己刚写的代码
- ❌ **禁止**: 引用 git diff 中你刚添加的内容

**检测伪完成的检查点**：
1. 声称"测试通过"但没有 `pnpm test` 输出
2. 声称"类型正确"但没有 `pnpm typecheck` 输出
3. 声称"功能正常"但没有实际运行证据
4. 引用 diff 中新增的测试文件（可能伪造）

### P4: 持久化交接
**每个 phase 写入计划文件/验收记录**

必须生成的文件：

```
round-XXX/
├── metadata.json          # 评审元数据（自动生成）
├── summary.md             # 汇总报告（自动生成）
├── phase-N-plan.md        # N 轮计划（自动生成）
├── phase-N-result.md      # N 轮结果（自动生成）
└── <reviewer>/
    ├── result.yaml         # 机器可读结果
    ├── score.md            # 评分详情 + 证据
    ├── blockers.md         # P0/P1 问题
    └── improvement-list.md # P2/P3 建议
```

### P5: Right-Size Throttle
**小改动不搞仪式，大改动强制流程**

规模检测与评审深度映射：

| 规模 | 检测条件 | 评审深度 | 自动化检查 |
|------|----------|----------|------------|
| Micro | ≤2 文件, ≤100 行 | 快速 | git diff |
| Small | ≤5 文件, ≤500 行 | 标准 | git diff + lint |
| Medium | ≤20 文件, ≤2000 行 | 完整 | git diff + test + typecheck |
| Large | ≤50 文件, ≤5000 行 | 深度 | git diff + test + typecheck + audit |
| XLarge | >50 文件, >5000 行 | 全面 | 所有检查 + 架构评审 |

## 证据类型详解

### 1. 代码证据

### 1. 代码证据

**来源**: 代码文件本身

**用途**: 证明功能存在、状态处理、错误处理等

**收集方式**:
```bash
# 查找关键代码
grep -n "async\|await\|then\|catch" --include="*.ts" | head -50

# 查找错误处理
grep -rn "throw\|Error\|reject" --include="*.ts" | head -30

# 查找状态处理
grep -rn "if.*null\|if.*undefined\|if.*empty" --include="*.ts" | head -20
```

### 2. 运行证据

**来源**: 实际运行程序

**用途**: 证明功能可用、路径正确、错误处理有效

**收集方式**:
```bash
# 构建验证
pnpm build 2>&1

# 测试运行
pnpm test 2>&1

# 类型检查
pnpm typecheck 2>&1

# Lint 检查
pnpm lint 2>&1
```

### 3. 截图证据

**来源**: UI 截图

**用途**: 证明视觉效果、交互状态、错误展示

**要求**:
- 标注截图对应的功能
- 包含正常和异常状态
- 清晰可读

### 4. 日志证据

**来源**: 程序输出日志

**用途**: 证明错误处理、请求流程、状态变化

**收集方式**:
```bash
# 服务器日志
tail -f logs/server.log

# 浏览器控制台
# (使用开发者工具导出)
```

### 5. Git 证据

**来源**: Git 历史

**用途**: 证明变更历史、代码演进

**收集方式**:
```bash
# 变更统计
git diff --stat

# 特定文件的变更
git log -p --follow -- "file.ts"

# 最近的提交
git log --oneline -10
```

## 必须收集的证据

### 产品闭环审查官

| 证据 | 来源 | 何时需要 |
|------|------|----------|
| 构建成功 | `pnpm build` | 每次评审 |
| API 路由可用 | curl 或代码检查 | 每次评审 |
| UI 组件渲染 | 截图或代码检查 | 有 UI 变更时 |
| 错误处理 | 代码检查 | 每次评审 |

### 工程架构审查官

| 证据 | 来源 | 何时需要 |
|------|------|----------|
| 模块边界 | 代码结构 | 每次评审 |
| 类型定义 | 代码检查 | 每次评审 |
| 依赖关系 | 代码检查或工具 | 架构变更时 |
| 循环依赖 | 工具检测 | 每次评审 |

### 验收发布审查官

| 证据 | 来源 | 何时需要 |
|------|------|----------|
| 测试通过 | `pnpm test` | 每次评审 |
| 构建成功 | `pnpm build` | 每次评审 |
| 类型检查通过 | `pnpm typecheck` | 每次评审 |
| E2E 测试通过 | `pnpm test:e2e` | 发布前 |
| 包发布成功 | npm/yarn 输出 | 发布时 |

### 破坏性质量官

| 证据 | 来源 | 何时需要 |
|------|------|----------|
| 安全扫描 | `npm audit` 或工具 | 每次评审 |
| 敏感数据处理 | 代码检查 | 有数据变更时 |
| 权限检查 | 代码检查 | 有权限变更时 |
| 输入验证 | 代码检查 | 有用户输入时 |

## 证据记录格式

每个 reviewer 应该在 `evidence.md` 文件中记录证据：

```markdown
# Evidence - [Reviewer Name]

## Build Evidence
```
[pnpm build output]
```

## Test Evidence
```
[pnpm test output]
```

## Code Evidence

### Error Handling

## Screenshots
![](./screenshots/feature-x.png)
```

## 门槛证据 (Gate Evidence) - 必须存在才能进入评审

门槛证据是进入评审的最低要求。如果任何一项缺失，评审无法开始。

### 门槛证据清单

| 类型 | 命令/来源 | 最低要求 | 缺失时 |
|------|-----------|----------|--------|
| 构建 | `pnpm build` | 成功退出 (exit 0) | ❌ P0 blocker |
| 类型检查 | `pnpm typecheck` | 0 错误 | ❌ P0 blocker |
| 测试 | `pnpm test` | 所有用例通过 | ❌ P0 blocker |
| 变更范围 | `git diff --stat` | 变更文件列表 | ⚠️ 警告 |

### 门槛证据收集流程

```bash
# 1. 构建验证 (必须成功)
pnpm build 2>&1 || { echo "BUILD FAILED"; exit 1; }

# 2. 类型检查 (必须通过)
pnpm typecheck 2>&1 || { echo "TYPECHECK FAILED"; exit 1; }

# 3. 测试运行 (必须全部通过)
pnpm test 2>&1 || { echo "TESTS FAILED"; exit 1; }

# 4. 变更统计
git diff --stat
```

### 门槛证据与评分的关系

| 门槛证据状态 | 对评分的影响 |
|--------------|--------------|
| 构建失败 | 直接拒绝，无法评分 |
| 类型检查失败 | 直接拒绝，无法评分 |
| 测试失败 | 直接拒绝，无法评分 |
| 全部通过 | 进入 Reviewer 评分阶段 |

## 证据质量标准

### 有效证据
- ✅ 直接引用代码行号 (如 `apps/local-server/src/goal/goal-loop-runner.ts:639`)
- ✅ 实际运行命令的输出 (如 `pnpm build` 输出)
- ✅ 带标注的截图
- ✅ 具体的错误信息

### 无效证据 (禁止使用)
- ❌ "代码看起来没问题"
- ❌ "应该可以工作"
- ❌ "根据经验判断"
- ❌ "初步测试没问题"
- ❌ 执行者的自我总结 (如 "我已完成了 X")
- ❌ 推测性的结论 (如 "可能存在 Y 问题")

### 证据可追溯性要求

每个评分结论必须能够回答：
1. **来源**: 这个结论的证据来自哪个文件/命令/操作？
2. **时间**: 证据是什么时候收集的？
3. **可复现**: 其他人能复现这个证据吗？

## 评审证据 (Review Evidence) - 按维度要求

评审证据是 Reviewer 在门槛证据基础上进行的具体检查。

| 维度 | 证据类型 | 格式 | 最低要求 |
|------|----------|------|----------|
| 功能完成度 | 实际运行输出 | 截图/日志/curl | 运行成功的证据 |
| 边界处理 | 边界测试用例 | 测试文件 | 每个边界条件有对应测试 |
| 错误处理 | 错误触发日志 | 错误输出 | 每个错误路径有触发测试 |
| 安全 | 扫描工具输出 | 安全报告 | `npm audit` 无 high/critical |

## 自动证据收集

| 证据类型 | 对评分的影响 |
|----------|--------------|
| 有证据 + 通过 | 不扣分 |
| 有证据 + 未通过 | 正常扣分 |
| 无证据 + 通过 | **最多给 75 分** (严格限制) |
| 无证据 + 未通过 | **必须提供证据，否则拒绝** |

## 常见证据缺失

| 场景 | 应该收集的证据 |
|------|----------------|
| 声称功能完整 | 实际运行截图或日志 |
| 声称错误处理完善 | 触发错误的日志 |
| 声称测试覆盖 | 测试输出 + 覆盖率报告 |
| 声称构建成功 | 构建输出 |
| 声称 UI 正常 | 截图 |

## 自动证据收集

review-gate.mjs 支持自动收集证据：

```bash
# 启用自动证据收集 (默认)
node review-gate.mjs --collect-evidence

# 跳过证据收集
node review-gate.mjs --no-collect
```

自动收集的证据包括:
- Git 状态和变更
- Package.json 信息
- 项目结构
- 构建输出 (如果构建已运行)
