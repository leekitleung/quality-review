# 评分一致性增强规则 (Scoring Consistency Enhancement Rules)

## 🎯 目的
确保所有Reviewer的评分在同一合理范围内，避免出现相同质量水平却得到30分差异化的结果。

## 📊 评分档位标准化

| 维度 | 90-95分应包含的内容 | 80-89分应包含的内容 | 70-79分离手就包含的内容 |
|------|-------------------|-------------------|-------------------|
| **功能完整性** | 核心路径100%可用，边界示例(空/null)测试完成 | 核心功能可用，有1-2个边界情况未完成 | 核心功能可用，边界缺失3+个 |
| **用户路径闭环** | 用户从A到B路径所有状态都有反馈 | 用户路径有断点，能恢复但需要刷新 | 用户路径有断点，某些状态无反馈 |
| **安全漏洞** | OWASP所有项SAFE，无红线 | 有1-2项AT_RISK但无完整漏洞链 | 有实现的安全漏洞需要修复 |
| **架构质量** | SOLID原则都符合，模块<1000行，无循环依赖 | 有1个超大文件或模块稍复杂 | 有多个架构问题或代码难以维护 |

## 🔍 跨Reviewer自动校准

Reviewer之间定期（每5轮）做一致性检查：

```bash
node scripts/consistency-checker.mjs \
  --rounds 10 \
  --threshold 15 \
  --output consistency-report.md
```

### 📈 一致性模型

当前:
- 平均分: 82 (sigma=5.2)
- 通过率: 68%
- 标准化提议: 将所有评分平均化到85±8范围

### 🛡️ 防止评分通胀

**硬性规则**:
- Reviewer不能因"友好度"而给高分
- 90分是通过门槛，不是"还不错"
- 70-75分代表"符合基本要求但能明显改进"
- <60分代表"不满足最低标准"

**反例处罚**:
- 如果一个文件有eval()就应该<=50分，不是可原谅的"架构问题"
- 漏掉所有输入验证就应该<=65分，不是"设计选择"

## 📝 标准评分模板

### Product-Flow Reviewer
```markdown
| 维度 | 满分 | 实际 | 扣分说明 |
|------|------|------|----------|
| 功能完成度 | 30 | 28 | 缺少单元测试: -1分 |
| 用户路径闭环 | 25 | 22 | 部分状态无反馈: -3分 |
| 状态完整性 | 20 | 18 | 无空状态处理: -2分 |
| 发现度 | 15 | 15 | - |
| 容错性 | 10 | 8 | 错误恢复需手动: -2分 |

**校准**: 28+22+18+15+8=91分 (>90通过)
```

### 架构Reviewer
```markdown
| 维度 | 满分 | 实际 | 扣分说明 |
|------|------|------|----------|
| 模块职责 | 25 | 20 | auth模块笨重: -5分 |
| 可维护性 | 25 | 22 | 部分重复代码: -3分 |
| 状态管理 | 20 | 19 | 无状态回滚: -1分 |
| 错误处理 | 15 | 13 | 部分错误无告警: -2分 |
| 可测试性 | 15 | 15 | - |

**校准**: 20+22+19+13+15=89分 (<90，但合理，因为架构较重)
```

## ⚖️ 评分验证对照表

| 当前评分 | 期望结果 | 需要改进 |
|---------|----------|----------|
| <60 | 🚫 应该重构 | 开发团队问题，过审无意义 |
| 60-75 | ❌ 严重不足 | 需要重大变更才能达到标准 |
| 75-89 | ✅ 中等，可接受 | 增加测试、文档、边界保护即可 |
| 90-100 | ✅ 优秀 | 装饰性改进可选 |

### 超过95分的门槛
Reviewer若给出95+的分数，需确保：
1. [x] 所有核心功能有端到端测试
2. [x] 架构有文档解释决策
3. [x] 安全评估无隐患
4. [x] 代码评审记录完整
5. [x] 发布检查清单完成

## 📋 每个评审员必须遵守的检查清单

开始评分前，Reviewer必须运行并确认：

- [ ] `npm run integrity-check` 检查缺少文件
- [ ] `npm run lint -- --max-warnings 0` 无风格问题
- [ ] `npm run typecheck` 类型正确
- [ ] `npm run test:core` 核心测试通过

评分过程中，Reviewer必须验证：

- [ ] 扣分项都有文件:行号引用
- [ ] 评分档位符合标准（见评分档位表）
- [ ] 分数变化合理化说明（如果跨轮次）
- [ ] 不因风格问题而扣分（除非影响维护性）

最终输出前检查：
- [ ] 检查destructive-qa是否标记风险
- [ ] 检查architecture-maintainer评论的复杂度是否影响功能性
- [ ] 确认所有P1问题在改进列表，无P0红线

## 🔒 评分断路器机制

当任何Reviewer评分存在以下情况时，自动触发人工审核：

1. **评分过高**（>95且该Reviewer历史平均分<85）
2. **评分过低**（<65且其他Reviewer评分>80）
3. **异常大幅波动**（单次评审分数变化>30分）
4. **缺少关键证据**（评分表中"证据"字段为空）

人工审核者在gate-check.mjs中强制覆盖评分并记录到元数据。
